# Серверные запросы фронта идут прямо в бэкенд, а не через Cloudflare

## Что было

18.08.2026, примерно с 18:01 до 18:27 по серверу, Cloudflare не мог установить
TLS-соединение с origin — часть узлов проходила, часть нет. Снаружи это выглядело
как ошибка **525 SSL handshake failed**: у одних сайт открывался, у других нет.

Сервер при этом работал: nginx обслуживал запросы каждую минуту всё окно,
не перезапускался, OOM не было, контейнеры не падали, сертификаты были валидны.

Но в логе контейнера `nextjs-prod` осталась запись:

```
18:01:26  [getStaticPage] Error: fetch failed  { code: 'ETIMEDOUT' }
18:27:19  [getStaticPage] Error: 525
```

То есть 525 получил не только посетитель — его получил **сам фронт от своего же
бэкенда**, стоящего в соседнем контейнере на этой же машине.

## Почему так вышло

В `.env.production` задан `NEXT_PUBLIC_API_URL=https://crysshop.kz`, и этим же
адресом пользовался серверный код Next (`getStaticPage` и остальные функции
`app/lib/data.ts`). Запрос из контейнера уходил петлёй:

```
nextjs-prod → интернет → Cloudflare → 86.107.45.211 → nginx → webshop
```

Хотя `webshop` — соседний контейнер. В результате рендер страниц на сервере
зависел от исправности внешнего канала, и заминка в Cloudflare ломала выдачу
целиком, а не только для тех, кто в этот момент был на сайте.

## Как сделано

Появился `app/lib/apiBase.ts`. Он возвращает разный адрес в зависимости от того,
где выполняется код:

- **в браузере** — `NEXT_PUBLIC_API_URL` (публичный домен, другого пути нет);
- **на сервере** — `INTERNAL_API_URL`, то есть `http://webshop` по внутренней
  сети Docker, минуя интернет, Cloudflare и nginx.

На него переведены все 52 запроса данных в `app/lib/data.ts` и запрос в
`app/proxy.ts`.

### Что НЕ переведено и почему

`src` картинок и ссылки, которые уезжают в разметку, по-прежнему строятся от
`NEXT_PUBLIC_API_URL` — их грузит браузер, и внутренний адрес там был бы битой
ссылкой. Это все вхождения в `app/components/**`, `app/ui/**`,
`app/dashboard/**`, а также `getOfferDocumentUrl()` в `data.ts` (ссылка на PDF
оферты).

**Правило:** через `apiBase()` проходит только `fetch`. Всё, что попадает в
HTML для браузера, — от `NEXT_PUBLIC_API_URL`.

### Инфраструктура

`docker-compose.yml` фронта подключён к сети `i-store_shop-network` (она
объявлена как `external`, создаёт её проект I-STORE). Отсюда следствие:
**бэкенд надо поднимать первым**, иначе сети не существует и фронт не стартует.

## Грабли

- `INTERNAL_API_URL` — обычная переменная окружения, не `NEXT_PUBLIC_*`.
  Она читается **в рантайме**, поэтому меняется без пересборки образа, и в
  клиентский бандл не попадает. Задаётся в `docker-compose.yml`.
- В разработке переменная не задана — `apiBase()` откатывается на
  `NEXT_PUBLIC_API_URL=http://localhost:5249`, поведение `npm run dev`
  не меняется.
- В `I_STORE.WEB/Program.cs` есть `app.UseHttpsRedirection()`, но контейнеру
  задан только `ASPNETCORE_HTTP_PORTS=80`, HTTPS-порта нет — поэтому редирект
  не строится и прямой HTTP работает. Если бэкенду когда-нибудь добавят
  HTTPS-порт, запросы на `http://webshop` начнут получать редирект, и это
  придётся учесть.

## Проверка паритета

Перед правкой все точки сверены: через nginx (`127.0.0.1:9090`) и напрямую
(`http://webshop`) ответы совпадают — `IndexJson` 200, `api/pages` 401,
`GetRegionsAndCities` 200, `GetProducts` 200, `GetOk` 404,
`api/pages/offer-document` 200.
